### 必须处理的具体差异

1. **建议等级 ≠ 考试硬条件。** Helper README 把 Ideal Lv. 与门槛混写；腾讯兵种表明确写「推荐 LV」。技能等级、考试票证、名声、篇章开放、特殊任务与建议等级必须独立存储。
2. **兵种数值冲突。** Helper 的 Warrior / Sniper 移动力为 6，现站勇士 / 狙击手为 5。没有确认游戏版本与原页前，不用其中一边覆盖另一边。两张 Game8 英文原页本轮 HTTP 402，未绕过访问限制，也未当作已复核。
3. **路线推荐是带目标的判断。** 腾讯新手表显示主观推荐：凯伊 B−、迪托利希 A−、赛奥朵拉 B、蕾达 A；同时写出凯伊抓宠耗时、迪线时间较宽裕。这支持拆开讲原因，不支持把表中评分直接替换本站「新手入门」与「四线整体养成」建议。
4. **强化值不可混在一栏。** 腾讯战技页表头说明括号内是深化后属性。应存 `base` 与 `enhanced`，而不是把 `2 (5)` 当字符串直接参与计算。
5. **缺失 ≠ 不存在。** 空白个人技、没有礼物记录、缺少主技能，分别保留「未收录 / 来源未给 / 待核对」；不能渲染成 0、不能学或不喜欢。

## 页面怎么重构

建议目标导航为「路线攻略 / 角色养成 / 资料速查 / 我的计划」；首页仍由品牌入口进入。现有 8 个入口按任务归并，来源档案进入页脚与各条资料出处。第一步只改角色与兵种内容结构，导航归并在完整页面迁移后再上线。

| 玩家要解决的问题 | 内容落点 | 主要接入资料 | 展示与操作 |
| --- | --- | --- | --- |
| 这个角色值不值得现在培养？ | 角色页默认视图 | 现站 build + 中文招募/角色表 | 先给作用、投入与取舍；按开局/中段/后期展开，数值放后面 |
| 怎样把角色练成我想要的样子？ | 角色页的成长、习得与兵种比较 | Helper 成长/法术/技能 + 腾讯中文技能表 | 基础成长、兵种加成、面板加成分开；技能反查「谁能学 / 何时学 / 用哪个兵种」 |
| 哪些伙伴与生活行动值得安排？ | 角色页支援与生活 | Helper 关系结构 + 腾讯礼物/吃饭/逗鸟 | 人物→支援对象→礼物/吃饭；未修订三人组合暂不做确定推荐 |
| 本线独有系统该怎样用？ | 各路线正文及角色关联入口 | 挑战书、骑乘指导、军团兵、饮料 | 挑战书→战技；骑乘→培养目标；军团兵→资源；饮料→效果与取得条件 |
| 为招到一个人还差什么？ | 既有招募规划与行程 | 当前交涉资料 + 腾讯挖角分配/道具/支线 | 从角色条件反查材料与请求，再进入路线行程；支持门槛与花费分列 |
| 一件物品或一种技能到底有什么用？ | 资料速查与统一搜索 | 武器、道具、特技、战技、魔法、血印 | 一个条目显示相关人物、取得条件、用途；共享同一份事实，不分别抄进多篇攻略 |

角色详情仍可从路线正文、搜索、招募规划打开；不要让玩家为了找一句信息连续跳四层。普通玩家默认看建议与行动，熟悉系统的玩家自行展开数字、关系和比较。主线任务不要被「资料施工进度」占据。

第一部沿用此前决定，不新增泛滥的剧透遮罩。实际接入第二、三部剧情细节时按当前站点约定处理；角色关系不应暗示第一部可跨线招募主角。

## 数据结构与导入边界

沿用静态构建。Helper 的约 7 MB SQLite 与抓取的 wiki 正文只作研究输入，不发到浏览器，也不移植整个 Helper UI。初期输出小的规范化 JSON，按人物/兵种/系统分片；页面、搜索和规划器共用，保持静态可阅读的详情链接。

每个实体保留稳定 ID、中文主名和中/日/英别名。先人工确认 ID 映射，别用近似字符串自动认人；图片编号不代替语义身份。现有 URL、锚点和分享码保持兼容，新别名只扩大搜索范围。

每个新增事实使用现有 `source/claim.schema.json` 的 `pending / provisional / confirmed / conflicting / withdrawn` 状态；通过附加字段表达 `entityId / field / value / unit / part / availability`。**availability 与可信状态分开**，建议值、推导值与硬条件也分开。`confirmed` 需要明确证据位置、审核人和日期；页面核对与游戏实测保留各自范围。

每条证据保存：来源 URL、上游 URL、Helper 提交号或表分页/行列、抓取日期、审查日期、游戏版本（不知道填 null）、路线、篇章、难度、独立性组、原始状态。公开来源不默认相互独立。Game8→Helper 是一条证据链；Helper 规划器还使用另一个社区 Google 招募表，单独记来源。

自动步骤止于候选：

```text
来源读取 → 保存可核对快照 → 别名与字段对齐 → 差异候选
                                      ↓
                           查原页 / 条件 / 版本 / 冲突
                                      ↓
                   人工审查的事实 → 静态页面、搜索、规划器
```

不要手工改 `source/sources.json`；它由 `tools/build_site.py` 生成。新来源应从实际引用它的源数据进入构建流程。

Helper 仓库本轮未找到 LICENSE，不整段移植其程序或界面。腾讯表索引有下载与转载使用说明；保留作者/共创表署名和原页入口，只整理经核对的必要事实，不批量镜像原表。若未来要复用代码或成批发布原表资料，另行确认相应授权范围。

## 未完成资料怎么给玩家看

- **可用部分先上线。** 例如挑战书先接已核对战技，资料缺口不阻塞整条路线；角色已有培养攻略即保留，不因缺礼物而隐藏整个人物。
- **缺口留在具体位置。** 没有确认学习条件就写「学习条件待补充」，不填默认等级。暂无任何有效条目的功能不做空菜单，保留对应资料入口即可。
- **冲突不变成计算输入。** 无法确认的移动力等字段不参与自动推荐；必要时展开看双方来源。
- **新资料不自动变答案。** 未修订支援组合、空白公式、缺后期方案的榜单进入维护候选队列。
- **前台轻、后台细。** 玩家通常只看到一行状态与更新时间，点击查看出处；逐字段差异、采集日志和抓取失败留在维护报告中。

## 实施顺序与完成标准

1. **先建立别名、来源与差异基线。** 本次已完成只读审计工具、字段摘要、计数校验和失败保护。下一步补实体别名映射、移动力等冲突核对；不以条目数量增长作为完成标准。
2. **优先发布角色与兵种的关联。** 先选 4 主角和已有培养方案的伙伴做完整闭环，再扩角色覆盖。每个页面至少能从培养方向查到考试条件与出处；旧深链接、FW1、本地计划、未知价格语义都保留。
3. **四线专属系统逐条接入。** 首批建议迪托利希挑战书；随后按照真实完成度推进凯伊骑乘指导、赛奥朵拉军团兵、蕾达饮料。每个条目都要有适用对象、效果、条件与来源，未完成部分不挡已确认条目。
4. **统一速查与全站导航。** 技能/物品的反查链路成熟后合并导航。公式有完整且核对过的输入、取整与适用条件之后，再考虑伤害模拟器。

现站现有 `profile.pilot.publishBattles=false` 保持。任何正式上线改动要跑项目要求的构建、Python/Node 测试、Chromium/WebKit、移动端、静态页面和部署检查；本次没有修改正式站点源内容或合并 main。
